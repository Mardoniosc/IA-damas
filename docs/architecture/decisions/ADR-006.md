# ADR-006 — Rules Core data structure: mailbox + precomputed rays, immutable API

- Status: **Accepted** (G2, 2026-11-20)

## Context

The Rules Core must be correct first (ADR-001), readable for rule audits, geometry-parameterized
(8x8 and 10x10, per ADR-005), and dependency-free. Speed matters less: the Rules Core validates
engine output and drives tests. The internal search (G8) is a separate concern.

Options considered:

| Option | Pros | Cons |
|---|---|---|
| Bitboards (Python ints) | fast perft in Python, compact | per-geometry shift tricks; harder to audit capture rules (majority, Turkish rule); 10x10 needs padding |
| **Mailbox (tuple of squares) + precomputed diagonal rays** | one generic code path for any even N; capture DFS reads like the rule text | slower (about 150k perft leaves/s) |

## Decision

- `Position.squares` is a tuple indexed by canonical square. `Geometry.rays[sq][dir]` holds the
  squares outward along each diagonal.
- Captures are found by a depth-first search over the rays. Captured pieces stay on the board
  during the search (Turkish rule) and are tracked in a list. Only maximum-length sequences
  are kept (majority rule), and they are deduplicated by `Move.identity`.
- The public API is immutable (`Position`, `Move`, `GameState`). Internals use local mutable
  lists.

## Consequences

- Measured performance: perft depth 8 from the Brazilian start in about 6 s. That is enough for
  validation and for depth-9 regression in the slow suite (about 2 min).
- G8 (internal search) will need a faster board, either bitboards or a native extension. It
  must be cross-checked against this Rules Core with the same oracle fixtures before use.
