# ADR-003 — Canonical position representation

- Status: **Accepted** (G1, 2026-11-20). Fields marked UNVERIFIED in the spec must be confirmed in G2.

## Context

Engines use incompatible formats: Hub uses a side char plus 50 squares (10x10), CheckerBoard
uses `int[8][8]` with bit-coded pieces and gametype-specific numbering. Human notations differ
too (algebraic vs numeric, and an unconfirmed numbering origin). The knowledge base needs a
stable key. Draw rules need history, not just a position.

## Decision

Adopt the representation specified in `docs/architecture/position-representation.md`:

1. Geometry-parameterized board. Brazilian 8x8 is primary, with canonical index
   `i = 4*rank + file//2` (0..31, a1 = 0, h8 = 31).
2. Immutable `Position` (squares + side to move) and `GameState` (position + history keys +
   draw counters + `ruleset_id`).
3. `Move` stores origin, ordered landing path, ordered captured squares and a promotion flag.
4. Canonical text form, the "DSA string" (side + 32 chars), plus a 64-bit Zobrist key. PDN FEN
   and algebraic notation are I/O formats handled by converters.
5. The only normalization symmetry is 180° rotation with color swap (`i → 31 − i`).
6. Engine formats exist only inside adapters.

## Consequences

- Converters are needed per engine and per notation. They are the place for gametype numbering
  differences.
- Draw-rule parameters are data in the ruleset, so a later rules clarification does not
  invalidate stored positions (only re-validation by `ruleset_id`).
