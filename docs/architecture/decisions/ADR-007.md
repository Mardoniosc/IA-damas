# ADR-007 — Engine search semantics: synchronous adapters, failures as data, stop-then-kill

- Status: **Accepted** (G3, 2026-11-20)

## Context

G3 implements ADR-002. Several behaviours had to be fixed precisely:

- what an adapter does when an engine is slow, silent, crashes or answers garbage;
- how many searches a process runs at once;
- how per-engine facts (score units, limits) are chosen without assuming capabilities;
- how lenient to be with non-standard Hub output.

## Decision

1. **One search per engine process, synchronous API.** `EngineAdapter.analyze()` blocks and
   is serialized by a per-adapter lock. Parallelism comes from several adapters (processes),
   which is G6's orchestration concern. An async/FastAPI layer will wrap adapters in worker
   threads rather than make them async.
2. **Search failures are results, not exceptions.** `AnalysisResult.status` is one of
   `ok | illegal_move | protocol_error | timeout | crashed`. Every anomaly is appended to
   `violations`, and the search's transcript slice is attached. Exceptions are reserved for
   lifecycle problems (`EngineStartError`, `EngineNotRunning`) and caller mistakes
   (`CapabilityError`, terminal positions).
3. **Deadline policy.** The budget is `move_time + search_timeout_s`. When it expires the
   adapter sends `stop` and waits `stop_grace_s` for the mandatory `done`. An answer received
   then is kept (`interrupted = True`). If none arrives, the process is killed
   (`timeout`), and the caller may `restart()`.
4. **Profiles come from evidence.** The profile is selected from the engine's own `id name=`
   line. Only `scan` has a specific profile (score unit "men", ±89/±99 bands, depth, nodes and
   move-time limits, all from its readme and protocol.txt). Every other engine gets
   `generic-hub` (depth and move-time limits, unit "unknown") until verified.
5. **Strict where it protects correctness, lenient where it doesn't.** Undeclared parameters
   fail the handshake. Unknown commands and arguments are ignored (spec). The non-standard
   short capture `from x to` is accepted **with a violation note** and resolved by the
   Rules Core, failing as ambiguous if needed. Illegal PV moves truncate the PV.
6. **Hub syntax is parsed to the spec**, not with shell-style tokenizing: there are no
   escapes and backslashes are literal (this fixes the G1 PoC limitation).

## Consequences

- Callers must inspect `status`. A non-OK result never carries a `best_move`.
- Throughput per engine is one position at a time. G6 must manage a pool.
- Kingsrow hub runs with the generic profile until G5 observes its real output.
